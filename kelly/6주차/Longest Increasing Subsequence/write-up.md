## 🧑‍🔬 문제 분석

정수 리스트가 주어졌을 때 해당 정수 리스트에서 가장 긴 순수 증가 시퀀스의 길이를 찾아 반환하는 문제이다.

- 자세한 내용은 문제를 참고하자.

문제에 주어진 제약 조건은 다음과 같다.

**Constraints:**

- `1 <= nums.length <= 2500`
- `104 <= nums[i] <= 104`

---

## 🤔 풀이 고민

### 혼자서 생각해낸 풀이

우선 완전 탐색을 사용할 수 있는지 살펴봤다. 문제에 주어진 리스트에서 구할 수 있는 모든 오름차순 시퀀스를 탐색하면서 최대 길이를 찾으려면 `O(N^2)`의 시간 복잡도가 예상되는데 문제에 주어지는 리스트의 최대 크기가 대략 `2 * 10^3`보다 크기 때문에 재귀 방식의 완탐은 아슬아슬하게 통과하거나 시간 초과가 발생할 확률이 높다.

- 엄연히 계산해보면 `O(N^3)`이 걸린다고 한다. 즉, 완탐으로는 풀 수 없는 문제이다.

그래서 더 빠른 풀이를 위해 DP를 활용할 수 없는지 살펴보니 쉽게 점화식을 도출할 수 있었다. 내가 도출한 점화식은 다음과 같다.

```python
# 점화식
f(n) -> 정수 n이 마지막 요소인 시퀀스 중 최대 길이 반환
f(n) = max(...f(m)) + 1, (m < n)

# Base case
f(0) = 1
```

위 점화식을 활용해서 코드를 작성하면 문제를 해결할 수 있다.

다만 내가 작성한 풀이는 시간 복잡도가 살짝 높아서 다른 사람의 풀이도 찾아봤다.

문제에서 목표하는 바는 엄격하게 오름차순이 유지되는 부분배열의 최대 길이를 구하는 것이다.

여기서 부분배열은 stable 해야한다. 즉 원 배열의 인덱스간의 선후관계가 부분배열에서 지켜져야 한다.

즉 `i` < `j` 일때 `nums[i]` < `nums[j]` 인 부분배열 이어야한다.

여기서 가장 길이가 긴 부분배열의 길이값을 반환하는 것이 문제에서의 목표이다.

그렇다면 가장 길이가 긴 부분배열을 구해야하는데 부분배열은 stable 해야한다(인덱스 간의 선후관계가 지켜져야함).

인덱스 `0` 부터 `nums.length`까지 임의의 인덱스 `i` 에 대하여 인덱스 `i` 가 마지막 원소인 부분배열의 길이를 저장하여 저장한 것들중 최대값을 구하면 된다.

여기서 값을 저장할때 임의의 인덱스 `i` 에 대하여 `j` < `i`  이며 `nums[j]` < `nums[i]` 인 임의의 `j`가 있다 가정해본다면

`dp[j]` 는 부분배열의 길이를 의미하는데 임의의 `j` 들중 `dp[j]` 의 최대값+1 이 `dp[i]`의 값이 된다.

예를들어 `nums = [8,9,10,2,3,11]` 이라 가정 해보자.

점화식은 다음과 같다.

$$
F(n)=\mathrm{max}(1,\ F(i)_{0\leq i<n \ \&\ \mathrm{nums}[i]<\mathrm{nums}[n]}+1) \\ F(0) = 1

$$

### 결론

- 내가 처음 생각한 점화식으로도 최종 정답 처리를 받는 코드를 작성할 수 있다.
- 다만 시간 복잡도가 살짝 낮은 편이라 찾아본 풀이로 구현하면 좀 더 빠른 코드를 작성할 수 있다.

## 🏃 코드 작성 과정

### 내가 처음 작성한 코드

```python
class Solution:
    def lengthOfLIS(self, nums: List[int]) -> int:
        # 메인 로직
        nums_size = len(nums)
        dp = [0] * nums_size
        dp[0] = 1

        for i in range(1, nums_size):
            dp[i] = max(dp[j] if nums[j] < nums[i] else 0 for j in range(0, i)) + 1
        
        return max(dp)
```

### 찾아본 풀이로 작성한 코드

```python
class Solution:
    def lengthOfLIS(self, nums: List[int]) -> int:
        # 메인 로직
        nums_size = len(nums)
        dp = [1] * nums_size

        for i in range(1, nums_size):
            for j in range(i):
                if nums[i] > nums[j]:
                    dp[i] = max(dp[i], dp[j] + 1)
        
        return max(dp)
```

- 내가 처음 작성한 풀이와 다른 사람의 풀이는 같은 점화식을 활용하는 같은 방식의 풀이 코드이다.
- 그럼에도 왜 내 코드보다 다른 사람의 코드가 더 빠른지 GPT에게 물어봤다.
- 결론은 내가 사용한 제너레이터 방식보다 순수 반복문이 더 빠르기 때문이다.
- GPT 답변

  # 1️⃣ 두 코드는 같은 풀이 방법을 사용해?

  **네. 완전히 같은 DP 풀이입니다.**

  둘 다 사용하는 점화식은 같습니다.

  dp[i] = max(dp[j]) + 1   (단, j < i 이고 nums[j] < nums[i])

  의미:

    - dp[i]
      → **i에서 끝나는 LIS (Longest Increasing Subsequence)의 길이**

  예시

  nums = [10, 9, 2, 5, 3, 7, 101, 18]

  예를 들어 `7` 위치에서는

  2 → 3 → 7

  2 → 5 → 7

  그래서

  dp[5] = max(dp[2], dp[3], dp[4]) + 1

  두 코드 모두 **O(N²) DP** 알고리즘입니다.
    
  ---

  # 2️⃣ 왜 다른 사람 코드가 더 빠를까?

  핵심 이유는 **generator expression 때문입니다.**

  Kelly 코드:

  dp[i] = max(dp[j] if nums[j] < nums[i] else 0 for j in range(0, i)) + 1

  이 코드 내부에서 실제로 발생하는 일은 다음과 같습니다.

  for j in range(i):
  if nums[j] < nums[i]:
  yield dp[j]
  else:
  yield 0

  즉 매 반복마다

    - generator 생성
    - 조건식 평가
    - yield 처리
    - max 계산

  이 **모든 과정이 한 줄 안에서 실행됩니다.**

  generator는 코드가 짧아지는 장점이 있지만

  **Python에서는 반복문보다 느린 경우가 많습니다.**
    
  ---

  # 3️⃣ 반면 다른 사람 코드

  다른 사람 코드:

  for j in range(i):
  if nums[i] > nums[j]:
  dp[i] = max(dp[i], dp[j] + 1)

  이 코드의 장점

  1️⃣ generator 생성 없음

  2️⃣ 조건 검사만 수행

  3️⃣ 바로 dp 값 업데이트

  즉 **불필요한 객체 생성이나 추가 연산이 없습니다.**
    
  ---

  # 4️⃣ 시간복잡도는 같지만 실제 실행속도는 다름

  두 코드 모두

  Time Complexity = O(N²)

  하지만 실제 실행에서는 다음 차이가 있습니다.

  | 코드 | 연산 |
      | --- | --- |
  | Kelly 코드 | generator + 조건식 + max |
  | 다른 코드 | 단순 반복문 |

  그래서 **실제 실행시간은 반복문 방식이 더 빠르게 나옵니다.**
    
  ---

  # 5️⃣ Python에서 특히 느린 요소들

  Python에서는 다음 요소들이 성능에 영향을 줄 수 있습니다.

    - generator expression
    - lambda
    - comprehension 내부 조건식
    - 잦은 함수 호출 (`max()` 등)

  Kelly 코드에서는

  generator + 조건식 + max()

  이 세 가지가 동시에 사용되기 때문에

  반복문 방식보다 느려질 수 있습니다.

  | 질문 | 답 |

  | 시간복잡도 | 둘 다 O(N²) |
  | 왜 다른 코드가 더 빠른가 | generator 및 추가 연산 overhead 때문 |

  # 🔥 참고 (LIS 더 빠른 풀이)

  LIS 문제는 **O(N log N)** 풀이도 존재합니다.

  핵심 아이디어는

    - 증가 부분수열의 끝 값을 관리
    - 이분 탐색(binary search)으로 위치 갱신

  시간복잡도

  O(N log N)

  코딩테스트에서는 보통 **이 풀이가 가장 많이 사용됩니다.**
